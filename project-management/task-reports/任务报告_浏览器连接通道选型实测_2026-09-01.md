## 1. 目标与结论（结论先行）

为「接口为主、UI 兜底」改造找一条**复用日常 Chrome 登录态、具备完整 CDP 能力、免重启/免重登**的连接通道。实测结论：

- **采用 `puppeteer-core` 经 Chrome 144+「运行时远程调试」通道连接日常 Chrome**（默认 Profile），授权弹窗用 macOS AX 的 `AXPress` 自动点，连接模块内置退避重试；
- Playwright（CLI / connectOverCDP）在该通道当前不稳定，弃用其连接层、保留扩展模式做 UI 兜底；chrome-devtools-mcp 不进运行时；裸 CDP 作为原理与保底。

## 3. 连接方式实测对照（精炼证据，避免重复试错）

| 方式 | 做法 | 实测现象 | 结论 |
|---|---|---|---|
| Playwright CLI `attach --cdp=chrome` | channel 名连接 | 端点被解析成**不带 UUID** 的 `/devtools/browser`，30s 超时 | 不通 |
| playwright-core `connectOverCDP`（带 UUID） | 编程式连接 | WebSocket `connected` 后等不到协议消息、超时；与官方 issue #40027 描述一致（v1.60 才着手支持） | 当前不用 |
| 裸 CDP（内置 WebSocket） | `attachToBrowserTarget{flatten}` + `setAutoAttach{flatten}` 后按 page session 收发 | 连通，实时收 Network 事件，百度 reload 见 93 请求/92 响应 | 可行但繁琐，留作原理/保底 |
| **puppeteer-core `connect(browserWSEndpoint=带UUID)`** | 加 `targetFilter:()=>true`、`handleDevToolsAsPage:true`、`defaultViewport:null` | **稳定连通**，`page.on('request'/'response')`/`evaluate`/`reload` 正常 | **采用** |
| `connect({channel:'stable'})` 自动发现 | 不读 DevToolsActivePort | 实验选项，本环境 connect 报 `The "path" argument ... undefined` | 暂不用 |
| chrome-devtools-mcp `--autoConnect` | MCP 服务器 | 能连，但面向 AI 宿主交互、多两层 stdio/Puppeteer，不适合无人值守 | 仅开发期可选 |
| HTTP 发现 `http://127.0.0.1:9222/json/version`、`/json/list` | curl | **恒返回 404**（该通道 WebSocket-only，无 HTTP 发现） | 404 属正常 |
| 页面级 `ws://.../devtools/page/<id>` 直连 | 裸 WebSocket | non-101 被拒；非 flatten 的 `sendMessageToTarget` 无回包 | 须走 browser 通道 + setAutoAttach |

> 正确会话姿势（裸 CDP 层面，便于理解 Puppeteer 内部做了什么）：连带 UUID 的 browser ws → `Target.attachToBrowserTarget{flatten:true}` 得 browser session → `Target.setAutoAttach{autoAttach:true,waitForDebuggerOnStart:false,flatten:true}` → 监听 `Target.attachedToTarget`，按 `type==='page'`+URL 选目标页 sessionId → 页面命令带 sessionId 复用同一 ws。

## 4. 关键验证数据

- **连接耗时**：多次自检 1.4～3.6s（含自动点授权）；
- **连续连接稳定性**：内置「403 退避重试」后连续 4 次连接全部成功；
- **抓包能力**：attach 现成百度标签 reload，共见 93 请求 / 92 响应（仅 1 个百度自身 `ERR_BLOCKED_BY_ORB`，无害）；`sniff_demo.js` 过滤 font/image/css/媒体后记录 57 条、输出 115 行请求/响应 JSONL；
- **页面读取**：`page.evaluate` 读到 `百度一下，你就知道`、`readyState=complete`；
- **无副作用**：`disconnect()` 后用户标签与登录态原样保留（未关闭任何页面）。

### 偶发 403 竞态及处理

一次紧接上次断开的新连接出现 `Unexpected server response: 403`；随后间隔 3s 与立即重连均成功，判定为「发起连接 ↔ 弹出授权窗」之间的偶发竞态（非频率硬限制）。对策：连接全程每 0.9s 代点授权，握手失败退避 1.2s 重试、默认 3 次；此后未再失败。

## 5. 授权弹窗实测（macOS AX）

- 弹窗为 Chrome 原生 sheet「要允许远程调试吗？」，按钮「在'设置'中关闭 / 取消 / 允许」；
- **按钮可见文字不在 `AXTitle`（为空），而在 `AXDescription`**；需 role=`AXButton` 且拼接 title/description/value/help 匹配；
- **坐标点击（System Events `click at` / cliclick）只会让 sheet 消失、并不真正授权**；对元素 `perform action "AXPress"` 才真正放行；AXPress 与屏幕坐标/多屏解耦，双屏下同样可靠（详见 [macOS 辅助功能自动化](../../docs/development/guides/macos-accessibility-automation.md)）；
- 该 sheet 对「整体读 entire contents」存在 AX 隔离，需递归逐元素遍历；
- **授权无法在设置中永久关闭**（Chrome 维护者称显式同意是刻意设计，官方讨论 #734），故自动 AXPress 是标准对策。

## 7. 一段环境插曲（与通道无关，记录以备排查）

排查中曾出现「Safari 能开百度、该 Chrome 打不开网页（`net::ERR_FAILED`），与 ClashX 系统代理开关无关」；`curl` 走代理/直连均正常，扩展（Adblock for Youtube）拦截特征不符。**用户重启长期运行的 Chrome 后恢复正常**，判定为旧 Chrome 主进程代理状态卡死；结论：浏览器整体打不开网页但系统网络正常时，先重启 Chrome，不要误判为 CDP 问题。测试连通性不要用网络不可达的域名（本次 example.com 在当前网络不可达，曾造成误导）。

## 10. 补测：Chrome 未运行自动拉起 + 授权链路三层根因修复（2026-09-01 晚）

### 10.1 Chrome 没开自动拉起、按 Profile 选择

- 本机 3 个 Profile：Default(jacky，`Local State` 的 `profile.last_used=Default`)、Profile 1(丽娟)、Profile 4(jack)；`DevToolsActivePort` 位于 user-data-dir 根、不随 Profile 变。
- 连接模块新增 `isChromeRunning / pickProfile / launchChrome / ensureChromeRunning`：未运行则按 `last_used`（无记录取第一个、存在 Default 优先）以 `open -a "Google Chrome" --args --profile-directory=<目录>` 拉起，轮询等端口文件两行就绪（默认 25s）再连。
- 冷启动无人值守实测：优雅退出 Chrome 后跑自检，自动以 `--profile-directory=Default` 拉起、生成**新 UUID**、自动连上（重启后 UUID 变化，再次印证必须动态读、禁硬编码）。
- 边界：远程调试勾选**按 Profile 记忆**；从未勾选过的 Profile 冷启动后不开端口，`ensureChromeRunning` 会超时报错并提示去该 Profile 勾选一次。

### 10.2 授权「时好时坏、偶发永久卡住」的三层叠加根因（均本机复现 + 修复验证）

| 层 | 现象/证据 | 根因 | 修复 |
|---|---|---|---|
| ①遍历过慢 | 手动点中一次实测 **9.27s**（进程 user CPU 仅 0.26s，其余全在跨进程 AX 等待） | 递归整张窗口、遍历网页 `AXWebArea` 上万节点，每节点一次 AppleEvent 往返；被 Node 侧 2.5s 单次超时杀掉，永远遍历不完 | 入口只取 `sheets of windows`、只在 sheet 内查找、遇 `AXWebArea` 即跳过、限深 12 → 同一点按 **0.31s** |
| ②并发堆积 | 卡住时 `ps` 见 node 派生一串 osascript 全部卡在 S 态（4s/3s/2s…无一退出） | `setInterval` 不等上次完成就并发派生，多个 AppleScript 在 System Events 串行拥塞、互相死等 | 改串行点击循环：同一时刻只一个 osascript、单次硬超时、停止时 kill 在途子进程 |
| ③失效子树 | 与 connect 并发时 osascript 退出码非 0（事已办成却报错） | 点中后 sheet 立即关闭，递归继续访问已失效元素；`perform action` 未容错 | 点中即停（gPressed 标志）+ perform/遍历全程 try；无弹窗/进程未就绪安静返回 `pressed=false`、退出码 0 |

逐级定位用的对照实验：独立 Node 用 `execFile` 单次跑同一脚本能成功（排除权限/TCC 差异）；手动单次耐心等 9.27s 也成功（证明不是「点不中」而是「太慢」）；`ps` 现场抓到 osascript 堆积（证明并发拥塞）。三条证据分别锁定一层。

### 10.3 修复后稳定性数据

- 连续 8 次默认自检：**8/8 成功**，单次整体 2.1–3.2s，每次结束 osascript 残留恒为 0；
- 冷启动无人值守自检通过（自动拉起 + 自动授权 + 连接，全程无需人工点）；
- 调试开关：`DEBUG_CDP=1 node scripts/cdp/connectBrowser.js` 打印每次点按的 pressed/耗时，便于复盘。
