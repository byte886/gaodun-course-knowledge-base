# 动态交互取证优先于静态逆向与纯接口复现

## 一句话结论
当静态读代码、离线"算"参数、纯接口复现卡死时，**不要继续闷头硬刚黑盒**；优先「让真实系统在真实界面里跑起来，用一次正常交互把证据"逼"出来，在对象之间的边界上截获」。离线复现失败往往不是"不可破"，而是缺真实运行环境 / 时序 / 实例上下文。本方法与 [故障排查先验顺序](standard-debugging-first-principles.md) 互补：后者管"先怀疑谁"，本页管"静态路线卡死时换什么路线取证"。

## 核心命题
密钥、运行态、临时凭证、内部状态这类东西，**只在"真实运行那一刻"存在于内存与消息流中**。读代码只能看到"机制"（知道要解密），动态交互才拿得到那个"具体实例"（真实 key）。ep3 取 key 是标准例证：离线调 authorize 全 40301、逆向 wasm 卡死，而 `gp.play()` 让视频真播后，在 Worker↔主线程通道里直接截到明文 key（见 [ADR-018](../../decisions/ADR-018-名师课ep3取流解密平台路由与平台字幕替代转写.md)）。

## 操作要点（按序）
1. **入口要对：沿真实用户导航路径定位运行态页面。** 不自己拼 URL、不在错误页面空转（26 考季页 `gp=undefined` 空转 vs 用户业务导航进入的真实播放页 `gp` 可用）。业务导航（大纲→讲→播放页）自带正确上下文。
2. **人机分工（最重要）**：**人提供业务路径 + 界面操作语义 + "正常该是什么样/哪里反常"；AI 负责挂观测点、截获内部状态、复现并固化。** 用户一次"从哪进、点哪"的界面指路，胜过 AI 十次离线盲猜；人对业务语义的掌握是静态分析补不出来的线索，要主动请人指路。
3. **让它真的发生，而不是模拟它发生。** 自动化新开的标签若播放器没真运行，可能只发出 OPTIONS 预检、真正 GET 不发出；必须用可观测信号（播放时间在走 / readyState / 状态位）**先客观证明"真的运行了"再取证**，避免在假运行环境里抓空。
4. **交互动作就是稳定复现的触发器。** 播放、切清晰度/线路、seek、翻页、提交会重走初始化 / 取密钥 / 建连；卡住时主动制造一次正常交互来逼出证据。
5. **观测点挂在"对象之间的边界"上**：线程/Worker 边界（postMessage）、网络边界（请求/响应）、模块边界（importKey/函数调用）。真实数据必穿越边界，在边界 hook 最省力，**不必钻进黑盒内部**（故不必逆向 wasm）。
6. **离线复现失败 ≠ 必须逆向。** 纯接口 403/CORS、wasm 难啃，先回运行态取证，成本通常远低于逆向；确认"必须真实运行时序/实例"后，就把"CDP 真实运行 + 边界截获"固化为正式链路，而不是继续追求纯离线。

## 适用与不适用
- **适用**：加密流密钥 / 临时 token / 运行态数据、前端黑盒（wasm、混淆 bundle）、接口有反爬时序校验、需要真实用户手势或播放才触发的请求。
- **不适用 / 先别上**：纯逻辑 bug（读代码 + 复算更快）、明确的参数/端点错误（先按 [故障排查先验顺序](standard-debugging-first-principles.md) 查自身）、可用只读接口直接拿到的数据（不必为它驱动整套 UI）。动态取证是"静态与离线路线被证伪后"的高成功率路线，不是默认第一步。
