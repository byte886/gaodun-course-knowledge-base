## 一、技术问题排查方法论（AI 侧）

### 1. 分层假设，逐层证伪（像剥洋葱）

把一条链路按依赖拆成有序层级，**从最底层开始，每层用一个最小探针确认通不通，再往上走**；卡在哪一层，问题就锁定在哪层，避免在上层反复猜测。

本次浏览器通道的分层排查链：

| 层级 | 最小探针 | 要回答的问题 |
|---|---|---|
| ① 端口监听 | `lsof -nP -iTCP:9222` | 通道到底起没起 |
| ② WebSocket 握手 | 裸 WebSocket 连端点 | 是连不上，还是连上后卡住 |
| ③ 授权 | 检测/点击授权 sheet | 是不是没点「允许」 |
| ④ 浏览器级命令 | `Browser.getVersion` | 握手后协议通不通 |
| ⑤ 页面会话 | `setAutoAttach` + 选中 page session | 能不能驱动具体标签 |
| ⑥ 业务请求 | `Network.enable` 看请求事件 | 能不能抓到真实流量 |

### 2. 最小探针优先于框架

在引入/怀疑高级框架前，先用**最原始的手段**看协议真实回包（裸 WebSocket、`curl -v`、原始日志）。框架是黑盒，会把底层现象包装成笼统的「超时」。本次正是裸 CDP 先跑通，才看清「Playwright 卡死」不是网络问题、而是它的会话协商与新通道不兼容。

### 3. 控制变量，做对照实验

一次只改一个变量，并主动设置对照组：手动点击 vs 自动点击、可达站点 vs 不可达站点、裸协议 vs 高级库、重启前 vs 重启后。对照组能把「相关」与「因果」分开。

### 4. 证据分级，结论标注可信度

`官方文档/源码 > 官方 issue/changelog > 权威社区实践 > 本机实测 > 推测`。写结论时标注属于哪一级，查不到就明说「不确定」，禁止用推测填补关键事实。

### 5. 先查官方、优先英文检索

- 查机制/接口优先官方文档与官方 issue；检索优先 Google/Brave，**技术问题用英文关键词命中率更高**；
- **链接 + 检索关键词双备份**：链接会过时/迁移，关键词能让任何人在未来重新定位到同类资料；
- 记录访问日期与当时的版本号（Chrome/Node/库版本），便于日后判断结论是否过期。

### 6. 失败两次就换通道，区分两类失败

- **瞬时错误**（竞态、时序、临时 403）：做有上限的退避重试即可，本次连接偶发 403 靠「重试 + 持续授权」吸收；
- **系统性不兼容**（某框架在某协议上根本不工作）：同一动作失败两次就换实现/库/路径，不重复撞墙，也不指望多试几次会好。

### 7. 「现象消失」≠「问题解决」，用底层状态复验

坐标点击让弹窗视觉关闭、连接却仍卡住——界面消失只是表象。**判断成功要以底层/业务状态为准**（握手是否真的建立、数据是否真的落库、提交是否真的被接收），不能只看 UI 变化。

### 8. 阶段性沉淀，避免上下文流失

每攻克一层，就把「可复用结论 + 可运行最小脚本 + 官方检索入口」固化到仓库；失败过程不必留档，但**从失败中得到的排障对策要沉淀**。长任务跨对话时，沉淀物就是下一个 AI 的接力棒。

### 9. 先怀疑自己，凭证/外部系统最后怀疑（先验概率原则）

**长期运行经验（约 10 天实测）：自动化任务失败，90% 以上是 AI/脚本自身问题，真正的凭证（token/登录态）失效不到 10%。请求用户登录是最后手段，不是第一反应。**

排查顺序严格按先验概率从高到低，不要跳步：

1. **先查 AI/脚本自身（九成问题在这）**：
   - 端点/域对不对（本次曾误打 `g-study/.../paper/create` 返回 404，实际做题走 `minerva` 域）；
   - 参数与 ID 对不对、是不是张冠李戴（本次刷新 token 时打开的是**税法课**页面 courseId=42660，而非目标**会计课** 42656）；
   - 输入文件的选取/排序/过滤逻辑（本次 `findJwt` 按文件名排序，新 token 被旧文件遮蔽——是代码 bug，不是 token 过期）；
   - 最近改动、断点续跑是否重扫、日志统计口径是否对。
2. **再查运行环境**：网络/代理、进程是否存活、依赖与解释器（如误用系统 python 缺 funasr）、磁盘内存。
3. **用硬证据验证凭证，不臆测**：必须发一次**真实只读请求**、明确返回「登录超时」业务码（高顿 553649434，HTTP 仍 200）才算 token 失效；**不能**凭「请求失败了」「JWT 的 exp 看起来快到了」「连续几张报错」就推断凭证失效——这些更可能是第 1 层的自身错误。
4. **最后才交用户登录**：仅当凭证确有硬证据失效、且自动刷新也失败、日常 Chrome 也未登录/需验证码时，才暂停交用户。

> 反模式：任务一失败就假设 token 过期、直接让用户重新登录。这既频繁打扰用户，又会用「换 token」这个动作掩盖真正的代码 bug——换完仍失败，还白白绕一圈。正确姿势是先用第 1、2 层自查排除自身问题，拿第 3 层的硬证据说话。

## 二、人机协作分工：哪些 AI 自动，哪些必须交人

### 1. 默认自动 vs 必须暂停交人

| AI 可自动（用户已授权、可逆/只读） | 必须暂停交用户处理 |
|---|---|
| 只读探测、本地脚本、抓包、日志分析 | **登录、验证码/人机校验、支付** |
| 本地环境配置、依赖安装、跑测试 | **不可逆提交**（如正式交卷、删除、发布） |
| 用户已明确授权的自动点「允许」类操作 | 账号/风控敏感、超出当前授权范围的动作 |
| 多方案对比、出文档、写并验证代码 | 需要人凭账号/身份/现实世界完成的环节 |

原则：**敏感与不可逆操作交人，其余尽量自动化，不把本可自动完成的事甩给用户。**

### 2. 「请人点一下做对照」是高效手段，不是失败

当某个自动动作反复失败、AI 无法判断是「自动化姿势错」还是「通道本身不通」时，请用户**手动做一次同样动作**，等于做一次高价值对照实验：
- 人手动也不通 → 通道/环境问题，别再纠结自动化代码；
- 人手动一通、自动不通 → 锁定在自动化姿势（如坐标点击无效、要用 AXPress）。
一次人工对照往往胜过十次盲试。

### 3. 用户的旁观观察是关键信号源

用户不操作时也在观察屏幕，能看到 AI 看不到的异常（本次用户发现「打开了不存在的 example.com」「开了 about:blank 又关掉」，直接推翻了 AI 的错误假设）。因此：
- AI 要**主动、简短地播报正在做什么**（开了什么页面/进程、准备点哪里），让用户的观察有对象；
- **鼓励用户随时反馈「我看到你在做 X」**，并把这类观察当作一等证据来核对，而不是当作干扰。

### 4. 双屏 / GUI 场景的配合

- 多屏找弹窗时先说明「我在找弹窗、不是需要你点」，避免用户误操作；
- 真正需要用户介入时明确说清「请点哪个按钮」，并在用户完成后让 AI 用底层状态确认结果；
- GUI 坐标类问题优先用元素级动作，详见 [macOS 辅助功能自动化](./macos-accessibility-automation.md)。

## 三、协作节奏（先讨论后执行）

1. **探查 → 约束 → 证据 → 执行 → 验证 → 交付**：先读全输入与现状，守住用户划定的范围，用证据支撑，再动手；
2. **决策点暂停**：根因、选型、schema、PoC 范围等关键节点先出方案、等用户确认再落地，不擅自扩大范围；
3. **方案阶段要挑战，不是迎合**：指出用户设想里的隐含假设、错误与遗漏；证据若指向相反结论，要敢于给出与用户倾向相反的推荐；
4. **用不同于生成路径的方式验证**：写了连接代码就真实连一次，写了文档就回读核对链接与数据，文件存在/语法通过不等于正确；
5. **交付要可直接使用**：给路径、给打开方式、给验证结果与遗留缺口，不交付半成品骨架。

## 四、反模式清单（不要做）

- 凭截图/视觉估坐标去点控件（多屏 + Retina 必偏，应读元素树）；
- 用网络不可达的域名做连通性测试（会把环境问题误判成程序问题），测试站点选稳定可达的；
- 硬编码每次重启都会变的标识（如 CDP 的 UUID 端点），应动态读取；
- 把框架层面的笼统「超时」直接当成网络故障，先下探一层看原始回包；
- 同一动作反复失败还重复试，不换通道也不请人做对照；
- 任务一失败就假设 token/登录态失效、让用户重新登录（九成是自身端点/参数/ID/选取逻辑错误，凭证失效须有只读请求返回「登录超时」的硬证据，见 §一.9）；
- 只看到弹窗消失/页面跳转就宣称成功，不核对底层状态；
- 用推测补关键事实、不给来源、不标访问日期。
