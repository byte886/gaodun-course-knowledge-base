# 通用交互流程与优化规范

> **文档类型**：Task（操作指南）
> **更新频率**：流程变更时
> **维护者**：AI自动维护
> **读者**：AI代理

> 本文档记录高顿平台（GlivePro）及其他Web应用自动化交互的通用流程规范、优化经验和踩坑总结。
> 适用于：做题、模考、视频播放、文档下载等所有需要通过Playwright CLI进行Web交互的场景。
> 特定场景的详细流程请参考对应文档（如做题流程参考 `exam-workflow.md`）。

## 一、页面管理原则

### 1.1 操作前检查（强制执行）

每次开始交互操作前，必须先检查当前浏览器的标签页数量和状态：

```bash
playwright cli -s=<session> tab-list
```

**检查清单**：
1. 当前有多少个标签页？
2. 哪个是当前工作页？
3. 是否有多余页面（已完成的页面、其他课程页面等）？
4. 是否有重复页面（同一页面打开多次）？

### 1.2 页面识别

- **当前工作页**：正在操作的页面，URL中包含当前任务的标识
- **多余页面**：已完成的任务页面、其他无关页面
- **异常页面**：ref失效、点击无响应、页面加载失败的页面

### 1.3 处理原则

1. 优先在当前工作页上操作
2. 多余页面**可以自动关闭**（Playwright CLI支持标签页管理）
3. 如果页面异常，先刷新页面或重新打开链接，不要在异常页面上反复尝试
4. 关闭多余页面时从后往前关闭（避免索引变化导致关错）

### 1.4 自动管理标签页

Playwright CLI提供完整的标签页管理命令：

```bash
# 列出所有标签页（含索引、标题、URL）
playwright cli -s=<session> tab-list

# 切换到指定索引的标签页
playwright cli -s=<session> tab-select <index>

# 关闭指定索引的标签页
playwright cli -s=<session> tab-close <index>

# 新建标签页
playwright cli -s=<session> tab-new [url]
```

**自动清理流程**：
1. 操作前执行 `tab-list`，识别当前工作页
2. 从后往前关闭多余页面
3. 只保留当前工作页，如需参考文档可额外保留1个页面
4. 关闭后再次执行 `tab-list` 确认

### 1.5 补题流程（通用，适用于做题、模考等场景）

#### 1.5.1 原则

**当系统提示有未做题时，必须通过答题卡单独挑选未做题，禁止从头依次重做。**

原因：从头依次重做会导致已做题被反向点击（取消选择），且浪费时间。

#### 1.5.2 正确流程

1. 打开答题卡（点击页面右上角"答题卡"按钮）
2. **批量识别未做题**：通过 JavaScript 遍历答题卡中的题号按钮，根据其样式状态（已完成/未完成的视觉标识）一次性识别所有未做题编号，无需逐题点击检查
3. 记录所有未做题编号列表
4. **逐个点击未做题编号**进入题目，**必须选择答案**（禁止只跳转不答题）
5. 每题选择答案后，确认选择状态（选项有选中标识），再进入下一题
6. 所有未做题完成后，再次检查答题卡状态，确认全部已完成
7. 已做题跳过，不要点击选项（避免反向取消选择）

#### 1.5.3 未做题识别方法

**方法一：批量识别（推荐）**

答题卡中的题号按钮通常有已完成/未完成的样式状态标识，可以通过 JavaScript 一次性批量识别：

```javascript
// 遍历所有题号按钮，根据样式状态判断是否已完成
const buttons = document.querySelectorAll('button');
const unanswered = [];
for (let btn of buttons) {
  const text = btn.textContent.trim();
  if (/^\d+$/.test(text) && text.length <= 2) {
    // 通过按钮的样式类（包含已完成标识，如 complete/answered/done 等）判断
    // 注意：不要依赖固定的 class 名，因为可能随页面更新而变化
    const isComplete = /complete|answered|done|已做/i.test(btn.className);
    if (!isComplete) {
      unanswered.push(text);
    }
  }
}
console.log('未做题编号：', unanswered);
```

**方法二：逐题检查（备选）**

如果批量识别不可靠，可以逐题检查：
- 点击题号跳转到该题
- 观察选项是否有选中状态
- 如果无选中状态，说明未做，进行作答
- 如果有选中状态，说明已做，直接跳下一题

> **注意**：
> 1. 样式类名可能因页面刷新或更新而变化，不要依赖固定的 class 名，应通过通用的已完成标识（如 complete/answered/done 等关键词）或视觉状态判断
> 2. 批量识别后必须逐个进入未做题并选择答案，禁止只记录编号不答题
> 3. 所有未做题完成后，必须再次检查答题卡状态，确认全部已完成后再交卷

## 二、强制执行检查清单

### 2.1 适用场景

适用于任何需要参考知识库、文档或其他参考资料的交互场景，包括但不限于：
- 做题（课后练习、模考、真题）
- 文档内容验证
- 数据录入与核对
- 任何需要基于已有知识作答的场景

### 2.2 检查清单（每步操作前必须确认）

每次操作前，必须按以下清单逐项确认，未确认不得操作：

1. **已识别任务目标**：确认当前操作的目标是什么（如：这道题考查什么知识点？）
2. **已查阅参考资料**：确认已查阅对应的知识库、文档或参考资料
   - 知识库位置：课程目录 `知识详解/NN_模块组/{官方知识点}.md`
   - 其他参考资料：根据具体场景确定
3. **已找到相关内容**：确认在参考资料中找到了与当前操作相关的内容
4. **基于参考资料操作**：确认操作是基于参考资料内容，而不是凭记忆或猜测
5. **易错点特别检查**：如果是易错点（如全站正确率<50%的题目），必须逐字核对参考资料中的表述

### 2.3 执行方式

- 可以使用 `grep` 命令快速搜索知识库中的相关内容：
  ```bash
  grep -r "关键词" 知识详解/
  ```
- 对于多选题，必须确认每个选项都在参考资料中有对应的依据
- 对于记忆模糊的内容，必须查阅参考资料，不能凭印象作答

### 2.4 违反检查清单的后果

- 如果发现操作时没有执行检查清单，必须立即停止当前操作
- 重新查阅参考资料
- 重新操作
- 将本次教训补充到对应文档中

### 2.5 效果验证

强制执行检查清单已在做题场景中验证有效：
- 税收立法与我国税法体系：5/5分，100%正确率
- 税收执法：8/8分，100%正确率
- 税务权利与义务：3/3分，100%正确率

对比之前未严格遵循检查清单时的错误（税法要素第6题，6/7分），证明检查清单非常有效。

## 三、结果读取规范

### 3.1 适用场景

适用于任何需要读取操作结果的场景，包括但不限于：
- 考试成绩读取
- 任务完成状态读取
- 数据验证结果读取

### 3.2 读取原则

1. **区分关键指标**：必须区分"本次结果"和"历史最佳结果"
   - 例如：考试成绩中，"得分"是本次得分，"最高得分"是历史最高分
2. **多字段交叉验证**：同时读取多个相关字段，交叉验证结果的准确性
   - 例如：考试成绩应同时读取得分、答对题数、正确率三个字段
   - 验证：得分 = 答对题数（每题1分），正确率 = 答对题数 / 总题数
3. **查看详细结果**：不能只看总分，必须查看详细结果（如错题解析、错误明细）
4. **使用可靠的读取方式**：优先使用 `eval` 执行JavaScript获取完整文本，避免snapshot深度不够导致信息缺失

### 3.3 考试成绩读取规范（强制执行）

```bash
# 使用eval获取考试报告的完整文本
playwright cli -s=<session> eval "document.querySelector('.exam-report, .report, [class*=report]')?.innerText || document.body.innerText.substring(0, 2000)"
```

**必须读取的字段**：
1. 考试名称
2. 得分（本次得分，不是最高得分）
3. 答对题数
4. 正确率
5. 总用时
6. 全站平均分（如有）
7. 击败同类考生比例（如有）

**必须查看的内容**：
1. 错题解析（哪道题答错了，正确答案是什么，解析是什么）
2. 作答情况（各考点的正确率）

### 3.4 禁止行为

- ❌ 只读取"最高得分"就当成是本次得分
- ❌ 不查看错题解析就记录成绩
- ❌ 不交叉验证得分、答对题数、正确率三个字段
- ❌ 使用snapshot深度不够就判断结果（应使用eval获取完整文本）

## 四、异常处理流程

### 4.1 页面异常

**症状**：ref失效、点击无响应、页面加载失败、元素找不到

**处理流程**：
1. 停止当前操作
2. 检查页面状态（`tab-list`、`snapshot`）
3. 如果页面异常，刷新页面或重新打开链接
4. 不要在异常页面上反复尝试
5. 如果刷新后仍然异常，记录问题并等待用户指示

### 4.2 操作异常

**症状**：点击后没有预期效果、选择状态不正确、自动跳题异常

**处理流程**：
1. 停止当前操作
2. 检查当前页面状态（`snapshot`查看元素状态）
3. 确认操作是否生效（如：选项是否被选中，蓝色圆圈是否出现）
4. 如果操作未生效，重新操作
5. 如果多次操作仍然无效，记录问题并等待用户指示

### 4.3 结果异常

**症状**：成绩读取异常、结果与预期不符、字段缺失

**处理流程**：
1. 停止当前操作
2. 使用 `eval` 获取完整文本，确认结果
3. 交叉验证多个字段
4. 如果结果确实异常，记录问题并等待用户指示
5. 不要凭猜测记录结果

### 4.4 Session连接异常与登录状态共享

**症状**：
- Playwright CLI命令响应缓慢或超时
- 重新打开session后跳转到登录页面，登录状态丢失
- `open`命令创建新的浏览器上下文，不共享用户已登录的Chrome状态

**根本原因**：
- Playwright CLI的`open`命令默认创建新的浏览器上下文，与用户正在使用的Chrome浏览器隔离
- 新的浏览器上下文没有用户的登录cookie和session，因此需要重新登录

**解决方案（已验证有效）**：

使用`attach --extension=chrome`模式连接到用户已经运行的Chrome浏览器，可以共享登录状态：

```bash
# 1. 关闭当前session（如果有）
playwright cli -s=<session> close

# 2. 使用extension模式attach到用户的Chrome浏览器
playwright cli -s=<session> attach --extension=chrome

# 3. 使用tab-new打开新标签页（共享登录状态）
playwright cli -s=<session> tab-new "https://目标网站URL"

# 4. 切换到新标签页
playwright cli -s=<session> tab-select 1
```

**关键要点**：
1. **必须使用`attach --extension=chrome`**，而不是`open`命令
2. **必须使用`tab-new`打开新标签页**，而不是在attach后的默认页面操作
3. **attach后的默认页面是Playwright扩展的连接页面**，不是目标网站
4. **用户的Chrome浏览器必须已经打开并登录**目标网站
5. **这种方式共享用户Chrome的所有状态**：登录cookie、session、缓存等

**判断是否需要重新连接的流程**：
1. 执行简单命令（如`tab-list`）检查session是否存活
2. 如果`tab-list`成功但其他命令超时，可能是页面状态问题，尝试刷新页面
3. 如果重新打开session后跳转到登录页面，使用`attach --extension=chrome`模式
4. 如果用户的Chrome浏览器没有打开，需要通知用户先打开Chrome并登录

**已验证场景**：
- 高顿平台（glivepro.gaodun.com）：attach模式成功共享登录状态，无需重新登录
- 分章真题测22题：使用attach模式完成全部题目，正确率95%

### 4.5 命令卡住/超时处理流程（分级处理）

**适用场景**：Playwright CLI命令执行时间过长、无响应、超时被移到后台。

**判断标准**：
- 简单命令（tab-list、eval获取URL）超过10秒无响应 → 可能卡住
- 复杂命令（snapshot深度>8、find大范围搜索）超过30秒无响应 → 可能卡住
- 命令被自动移到后台且TaskOutput无新输出 → 确认卡住

**分级处理流程（从简单到复杂，逐级尝试）**：

#### 第一级：轻量级恢复（优先尝试）

1. **检查session是否存活**：
   ```bash
   playwright cli -s=<session> tab-list
   ```
   - 如果成功 → session存活，问题可能是页面状态或特定命令
   - 如果失败 → session断开，跳到第三级

2. **检查当前页面状态**：
   ```bash
   playwright cli -s=<session> eval "window.location.href"
   ```
   - 如果成功 → 页面正常，问题可能是特定元素的ref失效
   - 如果失败 → 页面可能卡住，跳到第二级

3. **重新获取snapshot**：如果ref失效，重新执行`snapshot`获取新的ref

#### 第二级：页面级恢复

1. **刷新当前页面**：
   ```bash
   playwright cli -s=<session> eval "location.reload()"
   ```
   等待3-5秒后重新操作

2. **关闭多余标签页**：如果有多个重复标签页，从后往前关闭多余页面
   ```bash
   playwright cli -s=<session> tab-close <index>
   ```

3. **切换到其他标签页再切回**：有时页面焦点问题导致命令无响应
   ```bash
   playwright cli -s=<session> tab-select <other_index>
   playwright cli -s=<session> tab-select <target_index>
   ```

#### 第三级：Session级恢复（attach模式）

当第一级和第二级都无效，或者重新打开session后登录状态丢失时，使用attach模式：

1. **关闭当前session**：
   ```bash
   playwright cli -s=<session> close
   ```

2. **使用extension模式attach到用户的Chrome浏览器**：
   ```bash
   playwright cli -s=<session> attach --extension=chrome
   ```

3. **使用tab-new打开目标页面**（共享登录状态）：
   ```bash
   playwright cli -s=<session> tab-new "https://目标网站URL"
   ```

4. **切换到新标签页并验证**：
   ```bash
   playwright cli -s=<session> tab-select 1
   playwright cli -s=<session> eval "window.location.href"
   ```

#### 第四级：环境级恢复（最后手段）

当attach模式也无效，或者用户的Chrome浏览器本身有问题时：

1. **通知用户检查Chrome浏览器**：
   - Chrome是否正常运行？
   - 是否登录了目标网站？
   - 是否有弹窗或对话框阻塞？

2. **建议用户重启Chrome浏览器**：关闭所有Chrome窗口，重新打开并登录

3. **如果Chrome重启后仍然无效**：建议用户重启豆包应用

**重要原则**：
- ❌ 不要在卡住的命令上反复重试（浪费时间）
- ❌ 不要跳过分级直接使用最高级恢复（可能丢失上下文）
- ✅ 每级恢复后都要验证是否成功，再决定是否进入下一级
- ✅ 记录卡住的原因和解决方法，补充到本文档

**常见卡住原因与对应处理级别**：

| 卡住原因 | 症状 | 处理级别 |
|----------|------|----------|
| ref失效 | click/find报"ref not found" | 第一级（重新snapshot） |
| 页面加载慢 | eval超时但tab-list成功 | 第二级（刷新页面） |
| 登录状态丢失 | 跳转到登录页面 | 第三级（attach模式） |
| Chrome无响应 | 所有命令超时 | 第四级（重启Chrome/豆包） |
| 网络问题 | 页面加载失败 | 第四级（检查网络） |

### 4.6 入口找不到时的处理流程（3次尝试原则，强制执行）

**适用场景**：在课程表、学习空间、题库等页面中找不到目标入口（如课后练习、试卷、视频、文档下载等）。

**处理流程（必须严格执行，不得跳过）**：

1. **第1次尝试**：使用当前方法查找目标入口
   - 检查页面是否完全加载
   - 使用 `snapshot` 或 `find` 查找目标关键词
   - 滚动页面查看是否在可视区域外

2. **第2次尝试**：换一种方法查找
   - 使用 JavaScript (`eval`/`run-code`) 查找包含目标关键词的可点击元素
   - 点击展开相关课程/章节的详情
   - 检查是否有折叠/展开的内容

3. **第3次尝试**：再换一种方法查找
   - 刷新页面后重新查找
   - 从其他入口（如学习空间、题库首页）导航到目标页面
   - 检查页面是否有标签页切换、筛选条件等影响显示

4. **3次都找不到**：停止尝试，向用户说明情况并请求协助
   - 说明已经尝试了哪3种方法
   - 询问用户目标入口的位置或直接URL
   - 不得在未尝试3次的情况下就问用户

**禁止行为**：
- ❌ 第1次找不到就问用户
- ❌ 3次尝试使用同一种方法（必须换方法）
- ❌ 不记录尝试过程就放弃

**已验证场景**：
- 高顿课程表查找课后练习入口：3次尝试（snapshot查找、JavaScript查找、刷新页面）后仍找不到，需用户协助

## 五、多轮迭代测试优化流程

### 5.1 触发条件

当遇到以下情况时，应从主流程转入多轮迭代测试优化模式：

1. **新的交互场景**：遇到之前没有做过的交互操作（如：新的网站、新的功能、新的页面布局）
2. **效率不高**：当前交互方式效率低下，需要优化（如：多次点击失败、页面加载慢、操作步骤繁琐）
3. **准确性问题**：当前交互方式容易出错（如：选择状态不正确、结果读取错误、页面识别错误）
4. **用户反馈**：用户提出需要优化的场景

### 5.1.1 已处理交互场景记录

为了判断是否是新的交互场景，必须维护"已处理交互场景记录"。每次完成一个新的交互场景的多轮迭代测试优化后，都要将该场景记录下来。

**记录格式**：

|----------|-----------|-----------|----------|----------|----------|------|
| 高顿题库做题 | glivepro.gaodun.com | 课后练习/模考 | 2026-08-28 | 3轮 | exam-workflow.md | ✅ 已优化 |
| 高顿题库成绩读取 | glivepro.gaodun.com | 考试报告页面 | 2026-08-28 | 2轮 | interaction-workflow.md | ✅ 已优化 |
| 高顿题库页面管理 | glivepro.gaodun.com | 标签页管理 | 2026-08-28 | 2轮 | interaction-workflow.md | ✅ 已优化 |

**判断流程**：

1. 遇到新的交互操作时，先查阅"已处理交互场景记录"
2. 如果该场景已经记录且状态为"✅ 已优化"，则直接使用已优化的流程，不需要进入多轮迭代测试模式
3. 如果该场景没有记录，或者状态为"⏳ 待优化"，则进入多轮迭代测试优化模式
4. 优化完成后，更新该场景的记录（状态改为"✅ 已优化"，记录优化轮次和对应文档）

**维护原则**：

1. **及时更新**：每次完成新场景的优化后，立即更新记录
2. **定期审查**：定期审查记录，删除过时的场景，补充新的场景
3. **关联文档**：每个场景都要关联对应的优化文档，方便后续查阅
4. **状态追踪**：使用状态标记（✅ 已优化 / ⏳ 待优化 / ❌ 已废弃）追踪每个场景的状态

### 5.2 多轮迭代测试模式

进入多轮迭代测试模式后，按照以下步骤进行：

#### 第一轮：探索与记录

1. **探索交互流程**：手动或半自动地完成一次完整的交互操作
2. **记录问题**：记录遇到的所有问题（点击失败、页面异常、效率低下等）
3. **记录成功经验**：记录哪些操作是成功的，哪些方法有效
4. **初步分析**：分析问题的根本原因

#### 第二轮：优化与验证

1. **制定优化方案**：基于第一轮的问题记录，制定优化方案
2. **实施优化**：更新文档、调整操作流程、改进脚本
3. **验证优化效果**：再次完成一次完整的交互操作，验证优化效果
4. **记录新问题**：记录优化后仍然存在的问题或新发现的问题

#### 第三轮及以后：持续优化

1. **重复优化与验证**：根据上一轮的问题记录，继续优化
2. **直到达到预期效果**：当交互流程顺畅、效率高、准确性好时，结束测试
3. **一般需要2-3轮迭代**：大多数场景在2-3轮迭代后可以达到较好的效果

### 5.3 优化完成后的固化

当多轮迭代测试完成后，必须将优化结果固化到文档中：

1. **更新通用交互流程文档**：将通用的优化经验更新到本文档（interaction-workflow.md）
2. **更新特定场景文档**：将特定场景的优化经验更新到对应文档（如：做题流程更新到exam-workflow.md）
3. **更新脚本**：如果有脚本需要优化，更新脚本
4. **记录测试报告**：记录测试过程、问题、优化方案和最终效果

### 5.4 转回到主流程

优化完成并固化后，转回到主流程继续执行：

1. **确认优化已固化**：确认所有优化结果已经记录到文档中
2. **恢复主流程**：从之前中断的地方继续执行主流程
3. **应用优化结果**：在后续的交互操作中应用优化后的流程和方法

## 六、交互优化经验总结

### 5.1 效率优化

1. **批量查阅参考资料**：进入任务后，先快速浏览所有内容，识别所有需要参考的知识点，批量查阅参考资料，避免每次都搜索一次
2. **使用grep快速搜索**：使用 `grep -r "关键词" 知识详解/` 快速搜索知识库
3. **自动管理标签页**：操作前自动关闭多余页面，只保留当前工作页
4. **使用eval获取完整文本**：避免snapshot深度不够导致信息缺失

### 5.2 准确性优化

1. **强制执行检查清单**：每次操作前都确认已查阅参考资料
2. **多字段交叉验证**：读取结果时同时读取多个相关字段，交叉验证
3. **查看详细结果**：不能只看总分，必须查看详细结果（如错题解析）
4. **易错点特别检查**：对于易错点，必须逐字核对参考资料中的表述

### 5.3 常见错误与避免方法

| 错误类型 | 具体表现 | 避免方法 |
|----------|----------|----------|
| 凭记忆作答 | 不查阅参考资料，凭记忆操作 | 强制执行检查清单 |
| 混淆指标 | 把"最高得分"当成"本次得分" | 多字段交叉验证 |
| 页面管理混乱 | 多个页面同时打开，不知道在哪个页面操作 | 操作前检查标签页，自动关闭多余页面 |
| 信息读取不全 | snapshot深度不够，只看到部分信息 | 使用eval获取完整文本 |
| 异常处理不当 | 在异常页面上反复尝试 | 刷新页面或重新打开链接 |
