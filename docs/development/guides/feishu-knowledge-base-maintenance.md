# 飞书知识库整理与维护 SOP

> **文档类型**：Task（操作指南 — 飞书知识库维护）
> **更新频率**：整理方法或 lark-cli 用法变更时
> **维护者**：AI自动维护 + 用户审核
> **读者**：AI代理（开发工程师）与用户

> 本文只讲一件事：**如何整理和维护一个飞书知识库的结构**——盘点、归类、新建/移动/安全删除节点、为父节点写导航、交付前校验。
> 不涉及"本地文档 / 登录态如何同步到飞书"等内容关联问题（那是独立流程，不在本文范围）；`lark-cli` 的命令参数与报错踩坑统一见 [../api/feishu-api.md](../api/feishu-api.md)，本文只讲流程、原则与红线。

---

## 1. 整理结构 SOP（主流程）

对应 lark 工作流 `knowledge_organize`（移动属高风险，**方案必须先经用户确认**）。

1. **递归盘点（只读）**：从空间根逐层 `wiki +node-list`，拿到完整树（标题 / node_token / has_child / obj_type）。用脚本递归，不要只看一层。
2. **抽样读内容**：标题不足以判断归属的文档，用 `docs +fetch` 读开头（outline 级，不读全文）取证，不凭标题猜。
3. **出方案并暂停确认**：列出现状问题（同类分散 / 根目录散落 / 名实不符 / 父节点缺导航）+ 目标树 + 逐项移动清单（diff）。用户确认后才动手。
4. **先建后移、由浅到深**：先 `wiki +node-create` 建好目标分组并**立即记下 node_token**，再 `wiki +move` 移动。
   - 移动已有 wiki 节点用 **node 模式**（同步、保留 node_token 与正文，整棵子树随父移动）：
     ```bash
     lark-cli wiki +move --node-token <被移动节点> \
       --target-parent-token <目标父节点> --as user
     ```
5. **安全删除空节点**：`wiki +node-delete` **默认 `--include-children=true` 会级联删整棵子树**，删除前必须 `wiki +node-list` 核验**直接子节点数 = 0**，确认是空壳再删（`--obj-type wiki --yes`）；只删"内容已全部迁出、确认废弃"的空分组。
6. **写 / 更新父节点导航**（第 3 节）。
7. **覆盖校验**（第 4 节）+ fresh read 全树复核，输出"创建 / 移动 / 删除 / 失败"数量对照表。

## 2. 分类原则（通用方法，不预设某个库的固定结构）

1. **按主题归属分**，不按文件来源或产生时间分；一篇文档只归一个最贴合的父节点，避免同类内容散落多处。
2. **名实相符**：分组名必须等于其下内容主题；若一个分组长期装着异主题内容，应移动内容，而不是勉强保留分组名。
3. **何时再分一层**：当某分组下的内容能沿**单一清晰维度**切成两堆、且每堆都有多篇时才加子分组（例如某主题下按"是否编程自动化"切成"自动化 / 使用与配置"）；只有一两篇时不急着分层，避免空架子。
4. **层级别过深、单父节点下别堆太多**；建节点返回结构限制错误 `131003` 时，改放到更浅层级或换父节点，不要用同样参数重试。
5. **记原则、不硬背 token**：节点 token 在移动 / 重建后会变，按标题递归定位；拿不准归属先提方案确认，不擅自塞。

## 3. 父节点导航页写作规范（每个父节点都要有）

含子节点的父节点，正文都要有"**子节点链接 + 一句话摘要**"导航，让人点进去一眼看清每个子文档是什么。

格式：

```markdown
# <父节点标题>

本分组沉淀……（一两句说明这个分组管什么、建议阅读顺序）

## 文档导航（或"子分组导航"）

- [子文档准确标题](https://<租户域名>/wiki/<子节点 node token>)：一句话摘要，说明它解决什么问题、何时该读。
```

规则：

1. **链接文字必须等于子节点当前标题**；子节点改名后，导航链接文字同步更新（链接用 node token，仅移动不改名时 token 不变）。
2. **摘要必须来自子文档真实内容**（读其开头或其自带总览），不杜撰；每条一句话，讲"是什么 + 何时用"。
3. 子分组（还有下一层）和叶子文档都要列；子分组已有自己的导航时，父级只写该子分组一句总览，不重复其内部清单。
4. 已经正确的导航**不要重复 append**（会产生重复段落）；子节点增删 / 改名时用 `overwrite` 重写该父节点正文——重写前先 `fetch` 确认用户没在里面加过别的内容，有则保留。
5. 链接直接写**完整 https URL**，不要用变量 / 占位符（带引号 heredoc 不展开变量，占位符会变成坏链，踩坑见 feishu-api.md）。

---

## 4. 导航覆盖校验（交付前必跑）

不靠"看起来对"，用脚本比对：对每个父节点，取其**直接子节点 token 集合**，再取其**正文中出现的 `/wiki/<token>` 集合**，要求前者是后者子集（每个子节点都被导航覆盖），且正文无坏占位符。

```python
# 伪代码：children ⊆ linked
kids   = [t for t,_ in node_list(parent)]            # 直接子节点
linked = set(re.findall(r"/wiki/([A-Za-z0-9]+)", body(parent)))
missing = [t for t in kids if t not in linked]       # 必须为空
bad = "%" in body(parent)                            # 不应残留占位符
```

## 5. 新增单篇文档到指定节点下（基本操作）

1. 建文档并挂到目标父节点（`@file` 只接受当前 cwd 内的相对路径）：
   ```bash
   lark-cli docs +create --doc-format markdown \
     --content "@./xxx.md" --title "<文档标题>" \
     --parent-token <父节点 wiki node token> --as user
   ```
2. 给该父节点补一条导航（第 3 节）。
3. `wiki +node-list` 确认挂对位置、`docs +fetch` 回查正文渲染（表格 / 代码块 / 链接正常、无占位符残留）。

---

## 6. 安全红线

1. 移动 / 删除 / 重写前，先**只读盘点 + 方案确认**；非空节点不删、用户没明确同意不删。
2. 不修改与本次任务无关的文档；不覆盖用户在节点里手写的内容。
3. 不做 owner 转移、不改权限、不批量分享。
4. 任何写操作后都要 fresh read 验证；失败或不确定就如实说明，不假装成功。
